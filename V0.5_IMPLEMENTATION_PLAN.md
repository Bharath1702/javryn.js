# Javryn V0.5 — Explicit Parallel JavaScript Implementation Plan

> **Milestone Objective**: Introduce Javryn's first explicit parallel JavaScript API (`parallel.map`), a decoupled `TaskManager` for task distribution and result collection, function source serialization, worker pool reuse, ordered result collection, and error propagation without blocking the main event loop.

---

## 1. Current Baseline (V0.4 Worker Architecture)

In V0.4, Javryn established independent worker threads:
* **Workers**: Dedicated OS threads (`std::thread`), each owning an isolated `boa_engine::Context` and event loop.
* **WorkerManager**: Manages worker thread lifecycle, spawning, termination, and bi-directional message channels (`WorkerMessage`, `WorkerResponse`).
* **Serialization**: `JsMessage` type for thread-safe value transfer (`Null`, `Undefined`, `Boolean`, `Number`, `String`, `Array`, `Object`).

---

## 2. Target V0.5 Parallel Architecture

V0.5 introduces a layered architecture separating API, Task Management, and Worker Management:

```text
                    Javryn Runtime
                          │
                   Parallel API (JS)
                          │
                    Task Manager
                          │
                  Worker Manager
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
       Worker 1        Worker 2        Worker N
          │               │               │
       Boa VM          Boa VM          Boa VM
          │               │               │
      Event Loop       Event Loop      Event Loop
```

### Architectural Responsibilities
1. **Parallel API (`parallel.map`)**: Global JavaScript host API exposed to scripts. Validates inputs, serializes callback function source and input elements, creates an `OperationId`, and returns a JavaScript `Promise`.
2. **Task Manager (`TaskManager`)**: Owns `OperationId`, `TaskId`, input index mapping (`InputIndex`), task queueing (FIFO), worker assignment, result aggregation into ordered slots, cancellation, and Promise resolution/rejection.
3. **Worker Manager (`WorkerManager`)**: Manages the reusable pool of worker threads. Executes tasks by passing serialized callback source + argument payloads to workers.
4. **Workers**: Worker threads execute callback source in their local Boa context, return serialized `JsMessage` result, and remain ready for subsequent tasks.

---

## 3. Parallel API Design (`parallel.map`)

JavaScript usage:
```javascript
const results = await parallel.map(
    [10, 20, 30, 40],
    (x) => x * x
);
console.log(results); // [100, 400, 900, 1600]
```

### Execution Flow
1. Main script calls `parallel.map(items, callback)`.
2. Runtime converts `callback` to source code string (`callback.toString()`).
3. For each item in `items`, `TaskManager` creates a task with `(OperationId, TaskId, InputIndex, JsMessage)`.
4. Returns a pending JavaScript `Promise` to main script.
5. Tasks are dispatched to available workers in the `WorkerManager` pool.
6. As workers complete tasks, worker responses (`WorkerResponse::TaskCompleted`) are dispatched asynchronously through the main `EventLoop`.
7. `TaskManager` stores results into `results[InputIndex]`.
8. When all tasks for `OperationId` complete, `TaskManager` resolves the `Promise` with a JS `Array`.
9. If any task throws an exception, `TaskManager` rejects the `Promise` with the error and cancels remaining tasks for that operation.

---

## 4. Callback Serialization & Execution Model

* **Function Serialization**: Callback functions are converted to JS string source code (e.g. `(x) => x * x`).
* **Argument Serialization**: Input items are serialized into `JsMessage`.
* **Worker Execution**: Worker receives `WorkerMessage::ExecuteTask { task_id, fn_source, arg }`:
  - Evaluates `fn_source` to obtain callable function object in worker's Boa context.
  - Calls function with `arg.to_js_value(context)`.
  - Serializes return value to `JsMessage` and sends `WorkerResponse::TaskCompleted`.
* **Closure Boundary**: Uncaptured variables or non-serializable arguments return structured `RuntimeError::WorkerSerialization` or `RuntimeError::WorkerExecution`.

---

## 5. Result Ordering & Determinism

Even if tasks finish out-of-order due to variable execution times across workers, `TaskManager` maps each task back to its `InputIndex`:
```text
Task 3 (index 2) -> finished first -> results[2] = val3
Task 1 (index 0) -> finished second -> results[0] = val1
Task 2 (index 1) -> finished third  -> results[1] = val2
Result Array -> [val1, val2, val3]
```
Result array order is strictly deterministic and matches input array order.

## 6. Implementation Plan

1. **`javryn-runtime/src/tasks/`**:
   - `id.rs`: `OperationId`, `TaskId`.
   - `task.rs`: `ParallelTask`, `ParallelOperation`, `TaskState`.
   - `manager.rs`: `TaskManager` handling queueing, worker pool assignment, and result aggregation.
2. **Worker Protocol Extensions (`message.rs` & `worker.rs`)**:
   - Add `WorkerMessage::ExecuteTask { task_id: TaskId, fn_source: String, arg: JsMessage }`.
   - Add `WorkerResponse::TaskCompleted { task_id: TaskId, data: JsMessage }` and `WorkerResponse::TaskFailed { task_id: TaskId, error: String }`.
3. **Host Parallel API (`host.rs` & `event_loop.rs`)**:
   - Register global `parallel` object with `parallel.map(items, callback)`.
   - Update main `EventLoop` to poll `TaskManager` and resolve/reject JS Promises asynchronously.
4. **Testing Suite**:
   - `tests/javascript/parallel/basic_map.js`
   - `tests/javascript/parallel/cpu_map.js`
   - `tests/javascript/parallel/error_map.js`
   - `tests/parallel_integration_tests.rs`
   - `examples/parallel-map.js`, `examples/parallel-cpu.js`, `examples/parallel-error.js`
5. **Documentation & Benchmarks**:
   - `docs/PARALLEL_API.md`
   - Update `README.md`, `docs/ARCHITECTURE.md`, `docs/RUNTIME.md`, `docs/ROADMAP.md`
   - Benchmarks comparing sequential vs parallel execution in `tests/benchmark.rs`.
