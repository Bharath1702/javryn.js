# Javryn V0.3 — Implementation Plan: Async Runtime & Event Loop

## 1. Executive Summary & Context

Javryn V0.2 introduced JavaScript execution via `boa_engine`. V0.3 establishes a single-threaded asynchronous runtime and event loop. It enables `Promise` resolutions, `async/await` continuations, microtasks (`queueMicrotask`), and timers (`setTimeout`, `clearTimeout`, `setInterval`, `clearInterval`).

V0.3 remains strictly single-threaded from JavaScript's perspective:
`1 Runtime -> 1 JS Engine Isolate -> 1 Event Loop -> 1 Execution Thread`.

## 3. Event Loop Design & Execution Phases

The event loop coordinates execution in a deterministic sequence without CPU busy-spinning:

```text
1. Initial Script / Module Execution
             │
             ▼
2. Drain Engine Microtasks / Promise Job Queue (context.run_jobs())
             │
             ▼
3. Check Timer Queue (check due timers)
             │
   ┌─────────┴─────────┐
   ▼                   ▼
Ready Timers       No Timers Ready
   │                   │
   ├─ Execute JS       ├─ Pending Timers Exist? ──► Sleep until nearest deadline
   │  Callback         │                                       │
   │                   │  No Pending Work? ────────────────────┤
   ▼                   │                                       ▼
Drain Microtasks ──────┘                                  Event Loop Exits
(context.run_jobs())                                      Clean Shutdown
```

### Non-Blocking Sleep & Waking
- When no timers are ready but pending timers exist, the event loop calculates `duration = next_due_time - Instant::now()` and sleeps using `std::thread::sleep(duration)`.
- If `duration == 0` or negative, timers run immediately without sleeping.
- **Zero busy-spinning**: `loop { check() }` without sleeping is explicitly forbidden.

---

## 4. Timer Queue Architecture (`TimerQueue`)

### Structure & ID Generation
- `TimerId(u64)`: Monotonically increasing opaque 64-bit integer returned to JavaScript by `setTimeout` / `setInterval`.
- `TimerEntry`:
  ```rust
  pub struct TimerEntry {
      pub id: u64,
      pub due_time: Instant,
      pub delay: Duration,
      pub is_interval: bool,
      pub callback: JsValue,
  }
  ```
- `TimerQueue`: Maintains active timer entries sorted by `due_time`. Allows $O(1)$ inspection of the next deadline and cancellation by `TimerId`.

---

## 5. Host Timers & Microtask API Bindings

The host environment binds the following global functions into the JavaScript context during initialization:

- `setTimeout(callback, delayMs, ...args)` -> Returns `TimerId` (u64).
- `clearTimeout(timerId)` -> Cancels and removes timer.
- `setInterval(callback, intervalMs, ...args)` -> Returns `TimerId` (u64).
- `clearInterval(timerId)` -> Cancels and removes interval timer.
- `queueMicrotask(callback)` -> Enqueues microtask into the engine's microtask queue.

---

## 6. Microtask & Promise Integration

- Promise resolutions (`Promise.resolve()`, `Promise.then()`, `Promise.catch()`, `async/await`) schedule jobs into Boa's internal job queue.
- `context.run_jobs()` is invoked after:
  1. Initial script evaluation.
  2. Each host timer callback batch.
  3. `queueMicrotask` invocation.

### Unhandled Promise Rejections & Microtask Errors
- Exceptions thrown inside Promise continuations, `async/await` functions, or timer callbacks are captured.
- Uncaught exceptions interrupt event-loop execution and return `RuntimeError::JavaScriptExecution` with stack trace and file context, exiting with process code `5`.

---

## 7. Runtime Completion & Exit Rules

The runtime completes and shuts down cleanly when:
1. Initial script execution completes.
2. The engine microtask job queue is completely empty (`!context.has_jobs()`).
3. No active or pending timers remain in the `TimerQueue`.

If a script schedules `setTimeout(fn, 100)`, Javryn remains alive for 100ms, fires the timer, drains any resulting microtasks, and then exits cleanly with exit code `0`.

---

## 8. Ctrl+C & Shutdown Behavior

When a Ctrl+C (SIGINT) is received:
1. `interrupted` atomic flag is set.
2. Event loop stops processing new timers and cancels pending timer queues.
3. Runtime invokes `shutdown()` on engine and async runtime.
4. Process exits cleanly without deadlock or panics.
